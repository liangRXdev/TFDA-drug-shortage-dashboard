## 4. 平台限制與既有前提

- **GitHub Pages 純靜態**：無伺服器，所有狀態落在 repo 內 JSON。
- **dsms 可能封鎖境外 IP**：同機關的 `consumer.fda.gov.tw` 已證實封鎖 GitHub Actions IP；
  dsms 本機實測 HTTP 200；CI 可達性未驗證（本版不依賴，見 D3）。
- **dsms 為 ASP.NET WebForms**：GridView **非末頁每頁 13 筆**、末頁 1～13 筆，依更新日期新→舊；
  翻頁以 `__doPostBack('ctl00$ContentPlaceHolder1$grvDrug','Page$N')`，進詳情以列內
  `lbtnProductNameC` postback → 302 → `DrugInfo.aspx?No=<加密>&s=N&from=DrugList&r=<亂數>`。
  同一頁的 hidden fields 可以重複用來點該頁每一列。`s=1`、`s=5` 302 回首頁（非資料頁）。
- **請求量**：一輪完整列表約 51 個請求（約 30 秒）；每次執行兩輪列表，再加 `s=3`／`s=4` 每筆詳情（目前 244 筆，每筆 POST＋302 後 GET）與 `s=2` 新增成員的詳情（通常 0～數筆），間隔 0.5 秒，總計約 5～6 分鐘。
- **分頁列**：每頁都有分頁列，目前頁碼以 `<span>` 標示、其他頁為 `Page$N` 連結（每 10 頁一組，以 `...` 跳組）。末頁＝有目前頁碼標記、而且沒有下一頁連結。
- **本機排程依賴使用者開機**：Windows 工作排程器，`StartWhenAvailable=True`，僅登入時執行。
  2026-10-21～26 實際漏跑 5 天。本機執行沒有 6 分鐘上限。
- **每週 CI 會 commit 主檔**：本機 push 前必須先同步；兩邊改的是不同檔案，rebase 不會衝突。
- **PWA**：`vite-plugin-pwa` 的 runtimeCaching 目前只對 `supply_status_latest.json` 設 NetworkFirst，新檔需比照。
- **opendata 沒有案件編號**；dsms 有。許可證字號在 opendata 644 筆中**有 27 個重複**，
  無空值，含舊式「內衛藥製字」。`中文品名` 欄是「中文\n英文」合併字串，dsms 則中英分欄。
- **既有防線的實際強度**：`check_sanity` 的驟降只告警、不阻擋發布；前端 `isSupplyData`
  只驗頂層與資料集為陣列，不驗逐筆欄位。→ 補抓檔必須在前端做自己的逐筆驗證。
- **既有清洗語意（N2，不改）**：`cleanSupplyData` 會隱藏「同證號在 106 有日期 ≥ 本列日期」的
  104／105 列，並以 `theme|證號|日期|供應狀態` 去除完全重複列。補抓列走同一條管線，
  結果與「上游沒停更、opendata 本身就含這些列」時一致。
- **既有潛在 bug**：`App.tsx` 的 `DrugCard` key 以證號為主，同一月份同證號兩列會撞 key；
  補抓的修訂列會讓這種情況變常見 → 本增量一併修（key 改為內容身分，見 B9；不改視覺）。

## 5. 架構決策

| # | 決策 | 理由 | 不選的替代 |
|---|---|---|---|
| D1 | 補抓結果只寫新檔 `public/data/supply_supplement.json`，**絕不寫入** `supply_status_latest.json` | 每週 CI 以 opendata 全量覆寫主檔，併入的資料會被沖掉；並會污染 `upstream_max_date`/`frozen_runs` | 併入主檔：靜默資料流失＋停更偵測失準 |
| D2 | 差異在補抓端算好；前端的顯示結果 ＝ f(原始主檔, 補抓檔)，每次都從原始主檔計算，相同輸入得到相同結果，之後再交給既有 `cleanSupplyData` | 補抓端才同時看得到網站快照與主檔；從原始主檔計算，就不會對已套用的結果再套一次 | 前端自己推算：前端沒有網站快照；增量套用：多重集合重複消耗 |
| D3 | **本版固定本機排程**；CI 可達性探測只記錄結果，不切換，也不阻擋上線 | CI 可達性未證；同時規劃兩條發布路徑會加倍驗收量 | 先做 CI：可能寫完才發現抓不到；deploy.yml 也不吃 `GITHUB_TOKEN` 的 push |
| D4 | **按類別**判定成敗（s2/s3/s4 各自 `ok`/`error`）。失敗類別沿用前檔該類的上次成功結果（含其 `last_success_at` 與 `base`）；前檔沒有可用結果時，該類為 error 且沒有任何差異 | `s=2` 出錯不該擋住 `s=3` 新缺藥 | 全有全無：單點失敗遮蔽全部；按筆跳過：被跳過的往往是新公告 |
| D5 | **完整快照＋身分鍵＋內容指紋**。每類取得網站快照 L，與該類 opendata O 做多重集合差：`additions`＝L 中在 O 找不到相同身分與指紋的列（附完整欄位）；`supersedes`＝O 中在 L 找不到相同身分與指紋的列。**不以證號推測案件對應** | P1–P3 已實測成立；只有「網站快照中已不存在，或內容已變」才隱藏 | 證號＋日期推測（r1）：同證多案件會誤刪、修訂會重複 |
| D6 | **比較單位**：`norm(x)` ＝ NFKC 後去除全部空白。品名鍵＝`norm(中文品名第一行)`（主檔取 `\n` 之前；dsms 取中文品名欄）。`s=3`／`s=4` 的多重集合單位＝（品名鍵, 公告更新時間, norm(許可證字號), 指紋），指紋＝norm(供應狀態)。`s=2` 的單位＝（品名鍵, 公告更新時間），沒有指紋（N9）；s2 的 supersedes 另記該 O 列的證號，前端隱藏時品名鍵、日期、證號三者都要相符。差集、隱藏、略過新增**一律依單位與數量**判斷。主檔任一列的 `中文品名` 不是恰好含 1 個 `\n` → 該類 error、該列保留 | 列表沒有證號，詳情有；實測 10/10 指紋相等，代表指紋不會因格式差異大量誤判 | 只用證號：同證多案件；不做指紋：同日修訂看不到；只看存在性：碰撞群組會算錯 |
| D7 | **完整性與一致性守門**，任一條不成立該類即 error：（a）第 2 頁起每頁都必須有分頁列，目前頁碼標記等於預期頁碼（r5：只有一頁時 GridView 不輸出分頁列，第 1 頁沒有分頁列即視為單頁——這是殘餘限制的一部分）；末頁＝有目前頁碼標記、而且沒有下一頁連結；上限 40 頁（第 40 頁仍有下一頁 → error）；（b）非末頁每頁必須正好 13 筆，末頁 1～13 筆；（c）全類案件編號不重複；日期非遞增；（d）詳情頁的案件編號、品名必須等於列表該列；歷次表**最新一列**的日期必須等於列表日期，最新日期若有多列、內容不完全相同 → error；（e）同一單位在 O 或 L 出現超過 1 次、且兩邊次數不同 → error。**殘餘限制**：網站若穩定輸出外觀合法、但實際是截斷的分頁，偵測不到；D9 熔斷是最後防線 | 要隱藏 opendata 列，就必須證明快照完整，而且對象可以確認 | 允許碰撞時任選一筆：可能刪錯；用列數判斷末頁：滿 13 筆的截斷頁會被當成末頁 |
| D8 | **兩輪掃描**：每次執行依序掃 s3→s4→s2，再重複一輪；兩輪的列表必須逐列相同（案件編號、順序、日期、品名）。不同 → 整次重試一次（重試成功時只用重試的觀測結果）；仍不同 → 三類都 error（沿用前檔）。**觀測承諾**只到「兩輪列表一致，且每筆詳情的最新日期等於列表日期」；不宣稱整段執行期間內容都沒變 | 掃描中網站有變動時（翻頁位移、移類），單輪快照可能是不同時間點拼起來的 | 單輪：無法發現掃描中的變動；無限增加輪數：仍無法證明原子快照 |
| D9 | **熔斷**：`cap(c) = max(3, floor(0.02 × |O_c|))`；`supersedes` 筆數 > cap → 該類 error。不自動放寬；確認是真實的大量變動後，必須人工 commit 修改常數 | 網站改版或命名規則變動時，防止大量誤隱藏（＝漏報）；接受正常大量修訂時暫時誤報 error | 不設上限：一次改版就能把整區缺藥藏光 |
| D10 | **會讓缺藥消失的補抓輸入，有安全條件**：前端只有在「三類的結果都來自同一次執行、都是 ok、都新鮮，而且主檔 `last_updated` ≥ 每一類的 `base.last_updated`」時，才套用 (1) supersedes 與 (2) `s=2` additions（恢復公告會經由既有 zombie 規則隱藏缺藥）。條件不成立時**只套用 `s=3`／`s=4` additions**，並亮紅色警示，文案須寫明「可能有新舊版本並列，供應說明請以官網為準」。條件不成立的狀態可以長期持續（某類長期 error），不因時間經過自動恢復隱藏。**已接受的限制**：主檔在新鮮度窗口內（≤3 天）重新出現同單位的列時，仍會被隱藏，因為最近一次觀測顯示網站上沒有它 | 來源類別成功、目的類別失敗時，若照樣隱藏，公告會兩邊都消失（R4）；沿用的恢復公告會間接刪缺藥（S2）；比對單位含指紋，可避免舊指令誤藏內容已不同的列（R3） | 各類獨立套用：跨類移動時會漏報；只擋 supersedes：s2 恢復公告仍會間接隱藏缺藥 |
| D11 | 排程包裝沿用 recall 的 `update_supplement.py` 模式：`git pull --rebase` → 抓取 → 有變動就 commit/push → 全程 log。**有效的 error 快照也要發布**；push 被拒時 `pull --rebase` 重試一次，仍失敗就結束、不 force push；rebase 不改寫各類 `base`。exit 碼把抓取與發布分開：0＝全 ok 且已發布、2＝部分 error 且已發布、3＝發布失敗（commit 留在本機）、1＝主檔不可用、未寫檔。排程設 `MultipleInstances=IgnoreNew` 防重入 | 失敗狀態必須到得了前端；主檔與補抓檔是不同檔案，rebase 安全 | 只發布成功快照：失敗要等 3 天才被看見 |
| D12 | Python 用 `uv`、`requests` ＋標準庫 `html.parser`，不加 `bs4` | 依賴最少 | bs4：多一個依賴換不到必要能力 |

## 6. 資料流與契約

```
讀 repo 內 supply_status_latest.json（不可用 → 整批中止，exit 1）
第 1 輪：s3 → s4 → s2 列表全翻頁 ─┐
第 2 輪：s3 → s4 → s2 列表全翻頁 ─┴→ 逐列相同？否 → 整次重試一次 → 仍否 → 三類 error
s3、s4：逐列點進詳情 → 取歷次表最新一列（日期必須等於列表日期）→ 驗證（§6.2）
s2：列表比成員；只對新增的成員點進詳情取完整欄位
每類：D7 守門 → 依 D6 計算多重集合差 → D9 熔斷 → additions／supersedes
→ 原子寫入 public/data/supply_supplement.json（失敗類別沿用前檔）
→ update_supplement.py：commit + push → deploy.yml（push 觸發）→ Pages

前端：
  主檔載入（既有流程不變）∥ 補抓檔載入（NetworkFirst，逾時 8 s）
  逐筆驗證補抓檔
  顯示集合 ＝ 原始主檔
             − （D10 條件成立時）依單位與數量相符的 supersedes
             ＋ s3、s4 additions
             ＋ （D10 條件成立時）s2 additions
             （主檔已有同單位的列時，依數量略過對應筆數）
  → 既有 cleanSupplyData（不改）→ 顯示；補抓列帶「公告頁補抓」徽章，連到該類列表頁
  → 橫幅（§6.3）
```

### 6.1 補抓檔 schema（`schema: 1`）
```
{ schema: 1,
  generated_at: ISO8601+08:00,                 // 本次產檔時間，只寫 log；新鮮度不看它
  run_id: string,                              // 本次執行識別（產檔時間＋亂數）
  categories: { s2|s3|s4: {
     dataset: "54506_resolved" | "54504_with_alternative" | "54505_no_alternative",
     state: "ok" | "error",
     error: string | null,
     last_success_at: ISO8601 | null,          // 最後一次成功；失敗不前進
     success_run_id: string | null,            // 最後一次成功所屬的 run_id
     base: { last_updated, upstream_max_date } | null,  // 那次成功計算時用的主檔
     scanned: { pages, rows } | null,
     additions: [ { 編號: "dsms-<案件編號>", 公告更新時間, 中文品名: "中文\n英文", 許可證字號, 供應狀態,
                    _來源: "dsms", _案件編號 } ],
     supersedes: [ { 品名鍵, 公告更新時間, 許可證字號, 指紋 | null } ],
     excluded_no_license: [ { _案件編號, 公告更新時間, 中文品名 } ] } } }   // r5：空證號排除紀錄
```
D10 的「同一次執行」＝三類的 `success_run_id` 都等於頂層 `run_id`。

### 6.2 欄位有效性契約（Python 與 TS 共用同一份情境 fixture）
- 日期：`YYYY/MM/DD`，必須是真實日期，不得晚於執行當天（台灣時區）＋1 天。
- 許可證字號：符合 `(衛署|衛部|內衛)…字第[A-Z]?\d+號`（放射性藥品為「字第R00049號」，主檔有 14 筆）。
  **欄位存在但為空 → 該列排除**，不比對、不新增（使用者決策 A，2026-10-26）：這類是 opendata 本來就不收的品項，
  納入會讓差異永遠無法歸零、§8 退場條件永遠達不到。排除的列寫入各類 `excluded_no_license`（案件編號、日期、品名），
  不會靜默消失。欄位不存在（詳情頁結構改變）仍是違反契約。
- 案件編號：純數字，詳情頁的必須等於列表該列的。
- 中文品名：非空；英文品名可以為空（此時 `中文品名` 只有中文，不附 `\n`）。
- 供應狀態（詳情歷次表**最新一列**的「評估結果說明」）：非空，保留原文換行，只去除頭尾空白；最新一列日期 ≠ 列表日期，或最新日期有多列且內容不完全相同 → 違反契約。
- 類別：詳情頁跳轉網址的 `s=` 必須等於所在類別。

### 6.3 失敗行為
| 情況 | 補抓端 | 前端 |
|---|---|---|
| 該類任一列表／翻頁／詳情請求：網路、TLS、逾時、非 200、跳轉到非預期頁 | 該類 error，沿用上次成功結果 | 該類紅色、指名類別；不套用任何隱藏 |
| 列表有資料列但解析失敗、混有破損列、D7 任一條不成立、D9 熔斷、主檔有不支援的品名結構 | 同上 | 同上 |
| 任一詳情違反 §6.2 | 同上（不跳過那一筆） | 同上 |
| 兩輪掃描不一致（重試後仍是） | 三類 error | 三類紅色；不隱藏 |
| 列表區顯示「尚無資料」且沒有資料列 | L＝∅；supersedes＝全部 O_c，照常過 D9 熔斷 | — |
| 前檔不存在（首次執行） | 失敗類別：error、沒有結果 | 紅色 |
| 前檔損壞（JSON 壞、schema 不符） | 不沿用任何舊結果，視同首次 | — |
| 主檔不存在、JSON 壞、結構壞 | 整批中止、不寫檔、exit 1 | 補抓檔逐漸過期 → 紅 |
| 部分類別 error | 寫檔、包裝照常發布（exit 2） | 只套用 s3/s4 additions；紅色文案含「可能有新舊版本並列，供應說明請以官網為準」 |
| 發布失敗（push 重試後仍被拒） | commit 留在本機、exit 3 | 補抓檔逐漸過期 → 紅 |
| 補抓檔 404／500／JSON 壞／schema 不符／逾時 | — | 紅：無法載入補抓資料；主資料照常渲染 |
| 某類 `last_success_at` 缺漏、無法解析、晚於現在（r5：容許 5 分鐘時鐘偏差，補抓檔由使用者電腦產生）、或超過 3 天 | — | 該類紅：「N 天未更新」；不隱藏 |
| 主檔 `last_updated` < 任一類 `base.last_updated` | — | 紅：版本不一致，請重新整理；不隱藏 |
| 全部 ok、同一次執行、新鮮，且有差異 | — | 琥珀（資訊）：表中 N 筆由 dsms 補抓、M 筆已依官網更新 |
| 全部 ok、同一次執行、新鮮，且沒有差異 | — | 不顯示 |

紅色訊息可以並存，逐條列出、不互相遮蔽；並與增量 F 的停更橫幅並存。

## 7. 驗收條件

### A. 補抓端（pytest；fixture＝存下的 dsms HTML＋人工構造的反例）
- **A1** 列表→詳情對應：每筆 addition 的案件編號等於列表列；`供應狀態` 等於詳情歷次表**最新一列**的原文（含多段、換行、HTML entity、多個替代藥），只去頭尾空白。**正例**：（a）摩法爾 fixture（兩列 08/24、04/30）→ 取 08/24 那一列；（b）O 已有 X@10/07，網站同日期但最新一列文字不同 → 產生替換（完整流程，含詳情抓取）。**反例**，都要讓該類 error：（c）詳情換成相鄰案件；（d）詳情品名與列表不同；（e）歷次表最新一列的日期晚於列表日期（模擬列表抓完後網站更新）；（f）最新日期有兩列且內容不同。另測（g）最新日期有兩列且內容完全相同 → 視為一列，正常。
- **A2** 完整掃描：（a）正常 3 頁 fixture（13、13、7 筆）→ 請求頁序為 1,2,3，而且只在「有目前頁碼標記、沒有下一頁連結」時停止；（b）中間頁只有 12 筆 → error；（c）第 2 頁與第 1 頁內容相同 → error；（d）日期遞增 → error；（e）第 40 頁仍有下一頁 → error；（f）恰好 40 頁且第 40 頁是末頁 → ok；（g）第 2 頁滿 13 筆、但分頁列消失或目前頁碼標記不是 2 → error（不得以列數判斷末頁）；（h）跨 10 頁一組的 `...` 跳組正常運作。每一種 error 都要斷言該類結果等於前檔。
- **A3** 13 筆中有 1 筆欄位結構破損 → 整類 error，結果等於前檔；同一次執行中其他類照常更新（斷言另一類的 `last_success_at` 有前進）。
- **A4** §6.2 每條逐一違反（缺、空白、格式錯、未來日期、案件不符、類別不符）→ 整類 error；前 3 筆詳情正常、第 4 筆壞，也要整類 error，且 `last_success_at` 不前進。
- **A5** 「尚無資料」只在正確類別的列表區、且沒有資料列時才算 L＝∅。**反例**：200 但空白 body、首頁 HTML、錯誤頁、「尚無資料」與資料列同時出現 → 都是 error。O_c 非空時 L＝∅ 照常進 D9 熔斷（O_c＝5 → supersedes 5 > cap 3 → error）。
- **A6** 差異計算，每個情境都明列完整的 O、L（含背景列，使 D7／D9 守門通過）與期望的 additions／supersedes：
  - **s3／s4**（單位＝品名鍵＋日期＋證號＋指紋）：
    - 修訂（改日期）：O 有 X@05/07、L 有 X@10/16 → additions＝[X@10/16]、supersedes＝[X@05/07]
    - 修訂（不改日期，只改文字）：O 與 L 都是 X@10/07 但指紋不同 → additions＝[L 版]、supersedes＝[O 版]
    - 新增：L 有 Y@10/21、O 沒有 → additions＝[Y]
    - 同證另一案件：O 有同證 Z@2025/02 與 Z@2025/06，L 只有 Z@2025/06 → supersedes 只有 Z@2025/02
    - 同日期、同品名、不同證號：各自獨立比對，只隱藏網站上已不存在的那一筆
    - 同品名鍵＋日期＋證號兩筆，O 的指紋為 A、B，L 為 A、C → additions＝[C]、supersedes＝[B]
    - 同單位在 O 出現 2 次、在 L 出現 1 次 → error
  - **s2**（單位＝品名鍵＋日期）：
    - 兩邊都 2 次 → 無差異（對照奔麗生）
    - 同單位但文字不同 → 無差異（N9）
    - L 多 1 筆新成員 → additions 含完整欄位（證號、供應狀態取自詳情）
  - 品名或供應狀態只有空白／全半形差異 → 視為相同
  - 主檔任一列 `中文品名` 含 0 個或 2 個 `\n` → 該類 error，斷言 state＝error、該列不在 supersedes
  - 熔斷：|O|＝238 → cap＝4；supersedes＝4 → ok；＝5 → error；|O|＝100 → cap＝3；|O|＝149 → cap＝3；|O|＝200 → cap＝4
  - 輸入列順序打亂 → 結果相同
- **A7** 品名正規化：中英文都有、只有中文、英文含 `"`／全形引號／`/`／`&` → `中文品名` 字串格式與 opendata 同類列一致（以 COSOPIN、滅必治對照）。
- **A8** 主檔不存在、JSON 壞、`datasets` 缺鍵 → 各自 exit 1，補抓檔逐位元不變。
- **A9** 原子寫入：在寫暫存檔途中、以及替換前分別注入例外 → 舊檔逐位元不變；成功時新檔可完整解析且 schema 有效。
- **A10** 跨次序列（同一 fixture 流程連跑多次），每一步明列 O、各類 L、前檔與期望結果：
  ① O 沒有 X；s3 的 L 有 X → s3 additions 含 X；
  ② s3 失敗 → s3 additions 仍含 X、`last_success_at` 停在 ①、`success_run_id` ≠ 本次 `run_id`；
  ③ 網站把 X 從 s3 移到 s2，O 仍沒有 X → s3 additions 不再含 X（**不是**產生 supersedes），s2 additions 含 X 的**完整合法 record**（證號、供應狀態取自詳情）；
  ④ O 補上 X（在 106），而且 O 與網站其他部分也一致 → 三類的 additions、supersedes 都是 0；
  ⑤ 反例：O 有 W 在 104；網站把 W 從 s3 移到 s4；s3 成功、s4 失敗 → s3 supersedes 含 W，但頂層 run 不滿足 D10，前端不得隱藏 W（與 B2 對接）；
  ⑥ 反例：上一次成功時 s2 additions 含 V 的恢復公告（V 在 O 的 104 仍是缺藥）；這次 s2 失敗 → s2 沿用含 V 的 additions，但 D10 不成立 → 經完整前端流程與 `cleanSupplyData` 後，V 仍在 104；
  ⑦ 首次執行就失敗 → 該類 state＝error、沒有任何結果。
- **A11** 併發與發布（以模擬 git 驗證，斷言最終發布的檔案內容與 exit 碼，不只斷言指令出現）：（a）排程 XML 含 `MultipleInstances=IgnoreNew`；（b）全 ok、push 成功 → 發布內容等於本次結果，exit 0；（c）部分類別 error、push 成功 → 發布的是 error 快照，exit 2；（d）第一次 push 被拒、`pull --rebase` 後重試成功 → 發布內容的各類 `base` 等於計算當時的值（未被 rebase 改寫），從不 `--force`；（e）重試仍被拒 → commit 留在本機、exit 3；（f）主檔不可用 → 不 commit、exit 1。

### B. 前端（vitest）
- **B1** 確定性與正確性：A6 情境 fixture 帶**獨立寫定的期望輸出**，分別斷言「套用補抓後、清洗前」與「經 `cleanSupplyData` 後」兩個集合，逐列寫明保留哪一筆（含指紋）；TS 結果必須等於期望輸出，而不只是等於 Python 的結果；同樣輸入呼叫兩次結果相同；輸入物件不被修改。重數情境：O 同單位 2 筆（指紋 A、B）、supersedes 只有 B → 最終只少 B 那一筆。
