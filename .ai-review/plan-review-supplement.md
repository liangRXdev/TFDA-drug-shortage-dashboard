## 2. 架構風險

### 2.1 High／D5 的匹配資訊不足以判定案件已被收錄或已恢復

- **問題：** 同證號案件 A 於 10/01 缺藥，案件 B 於 10/20 恢復，D5 會讓 B 刪掉 A。反過來，opendata 有 B 的較新資料，也不能證明 dsms 較舊的 A 已收錄。日期代表更新時間，不是案件身分。
- **晚修成本：** 這會決定哪些資料在補抓端被永久排除、哪些缺藥被前端刪除，是最難回頭的決策；後續測試與資料模型都會依附錯誤語意。
- **建議修法：** 將「已確認同案件／同公告」與「僅同證號、無法確認」分開定義。dsms 內以案件編號辨識修訂及移類；跨來源無法確認時，不得只憑證號及日期宣告恢復或已收錄。保留缺藥證據並明示狀態待核對；不能把兩列都呈現成無條件成立的目前狀態。這可維持獨立 supplement JSON，不必修改主檔 schema。

**限制須明說：** 在 opendata 沒有案件編號、也未證明存在其他可靠對應資訊的前提下，無法同時保證「自動精準替換所有案件」與「絕不誤刪另一案件」。規格必須接受保守歧義處理。

### 2.2 High／D5、A6 與 B3 的預期互相衝突

- **問題：** 主檔 X 有 10/01、10/25，補抓 X 為 10/20。A6 規定補抓剔除；D5／B3 則指向替換較舊列、保留較新列。前者可能保留兩筆主資料，後者則產生 10/20 補抓與 10/25 主資料。
- **晚修成本：** Python 與 TS 即使各自通過驗收，也可能遵守不同規則；重新統一時要重做兩端及 fixtures。
- **建議修法：** 先依 2.1 定案案件對應語意，再列出每個案例的**完整輸出集合、類別、來源與警示**。不得以「剔除」「替換」兩個動詞代替最終結果。

### 2.3 High／既有清洗會再次推翻補抓的案件保留規則

- **問題：** [dataPipeline.ts](C:/Users/liang/projects/TFDA-drug-shortage-dashboard/src/lib/dataPipeline.ts) 的 `cleanSupplyData` 以證號的最大恢復日期，移除日期較早或相同的 104／105 列；完全重複判定也不包含案件編號。即使補抓合併保留了另一案件，下一段仍可能刪掉它。
- **晚修成本：** 單測合併函式會通過，只有完整 UI 才漏報，屆時必須重訂整條管線契約。
- **建議修法：** 把「不得因別案恢復而刪除缺藥」定為合併至最終顯示的共同不變條件。若「主檔流程不變」包含禁止調整這段行為，則與保留多案件目標衝突；相容作法是讓補抓及待核對案件不受原有證號級清除規則裁決，而維持純主資料既有流程。

### 2.4 High／D4 的舊 records 缺少跨類別有效性規則

- **問題：** s3 沿用案件 A 的 10/15 缺藥，s2 成功取得 A 的 10/20 恢復；或 s2 沿用舊恢復，s3 成功取得同案件的新缺藥。D5 只描述補抓對主檔，沒有補抓對補抓、跨類別不同查核時間的優先序。
- **晚修成本：** 各類獨立成功的模型上線後，才補跨類裁決，會牽動 records 與狀態語意。
- **建議修法：** 定義同案件跨類移動及修訂的唯一有效版本；無法確認時保留缺藥、顯示待核對，不把舊恢復當作刪除依據。

**對指定疑問的直接回答：** 若 D5 的日期比較正確，舊補抓不應直接替換日期較新的 opendata。但這不代表安全：它仍可能刪除同證號其他較舊案件，或透過既有清洗刪掉缺藥列。若日期代表內容修訂而非狀態先後，單純新舊比較本身也不足。

### 2.5 High／D6 的全域日期窗口無法證明 G1 已完成

- **問題：** 104 前進到 10/21，106 仍停在 9/01；106 在 9/20 的漏收公告可能位於停止頁之後。另有原先保留的缺口，隨主檔最大日期推進而落出窗口，成功重抓就可能把它清掉。
- **晚修成本：** 若只儲存窗口內差集，事後無法區分「上游補齊」與「不再掃到」，須重建保留與完整性語意。
- **建議修法：** 明定何種證據足以宣稱掃描完整，不能以其他類別的最新日期證明本類無缺口。已知未解缺口不得只因離開窗口消失；若上限內無法證明完整，須 error 並保留舊資料。即使改用各類最大日期，也不能單獨證明較早公告沒有漏收。

另須區分「第 5 頁已證明到末頁」與「第 5 頁後仍有未檢查資料」。目前一律觸頂失敗雖保守，但未定義末頁、日期等於門檻、排序破壞、重複頁與翻頁期間新增公告的處置。

### 2.6 High／D7 的差集與前端主檔可能不是同一版本

- **問題：** 補抓端依主檔 M2 將 records 歸零，前端卻因獨立快取讀到 M1。已被差集剔除的公告不在任何前端輸入裡，再跑 D5 也救不回。`opendata_max_date` 相同不代表主檔內容相同。
- **晚修成本：** 需要補充補抓檔的基準識別／相容性資訊，並重做快取及零筆狀態驗收。
- **建議修法：** 明定差集只能與相容主檔一起宣告「零缺口」；不相容時顯示紅色不完整警示。基準識別可放 supplement，不必修改主檔 schema，也不需要跨檔原子下載服務。

### 2.7 Medium／D3 的 CI 成功定義與部署前提不成立

- **問題：** GET s3 的 HTTP 狀態與 body 長度，無法證明翻頁、詳情及其他類別可達。[deploy.yml](C:/Users/liang/projects/TFDA-drug-shortage-dashboard/.github/workflows/deploy.yml) 目前只承接原本資料更新 workflow 的成功結束；`GITHUB_TOKEN` push 不會自行觸發另一個 push workflow。
- **晚修成本：** CI 抓取成功、repo JSON 已更新，Pages 卻不變；全 error 快照也可能被成功條件攔住。
- **建議修法：** 將單次 GET 定位為初篩；改用 CI 前須證明實際所需完整路徑可用，並驗收正常與 error 快照都能抵達 Pages。保留本機預設即可符合既定限制。

## 1. 新模型的漏報路徑與規格矛盾

### R1｜High｜K 相等只能證明列表鍵相等，不能證明內容相等

- **問題：** O、L 的類別、品名、日期相同，但網站修訂了替代藥清單，則 additions、supersedes 都是零。詳情只抓 additions，因此修訂完全不可見，最後還可能符合退場資格。實測證明「有案件修訂時改日期」，不能推導成「所有修訂必改日期」。
- **晚修成本：** 這決定差異的定義、需取得哪些資料，以及 schema 是否需要表達同鍵替換；上線後才補會重動資料流。
- **建議修法：** 明確定案 G1 是「列表成員差異」還是「公告內容差異」。若維持目前模型，必須明文承認同鍵內容修訂不受涵蓋，不能將零差異描述成內容已同步。  
  **[新增需求] 同鍵供應狀態修訂偵測：** 若要涵蓋使用者本輪指定的同日修訂情境，須把它明列為目標；不做的具體後果是網站已更正替代藥清單，看板仍顯示舊文字且沒有警示。這不能靠目前的列表鍵判定補救。

### R2｜High｜多重集合差沒有足夠資訊辨認要新增或隱藏哪一筆

- **問題：**
  - O 有兩筆同 K、不同證號或不同供應狀態，L 只有一筆。列表未提供證號，無法知道留下的是哪一筆；supersedes 另記證號，只是記錄選擇結果，沒有增加選擇依據。
  - O 有一筆同 K，L 有兩個不同案件同 K，前端「主檔已有同 K 就略過」會把必要 addition 跳掉。
  - O 有兩筆、supersedes 要移除一筆：若每次套用都再消耗一筆，第二次會清成零，與 B1 冪等要求衝突。
- **晚修成本：** 會牽動差集身分、supplement schema、前端套用契約及兩端共用 fixture。
- **建議修法：** 定義同 K 群組中如何確認各筆對應、隱藏數量及套用基準。資訊不足的碰撞不得任意選一筆刪除；可用既有類別 error 處理，無須新增 UI 狀態。區分「每次由原始主檔計算顯示結果」與「對已套用結果再次操作」，不要同時要求無法保證的多重集合消耗與冪等。

### R3｜High｜D9 的跨版本安全主張錯誤，且全檔 base 無法代表沿用結果

- **問題：**
  1. 舊補抓包含 X 的 supersedes。較新的主檔重新納入相同 K、相同證號的 X，可能是重新刊登或同日內容修正；舊 supersedes 仍會隱藏它。`last_updated` 較新不會阻止操作。
  2. 某類沿用昨天的差集，其他類今天成功；schema 只有一個全檔 base，無法如實表示不同類別差集各自依據的主檔。
  3. `last_updated` 是 ETL 成功檢查時間，不是資料內容身分。時間前進不能證明舊隱藏指令仍有效。
- **晚修成本：** 需要調整差集基準的資料契約及相容性規則，屬資料模型層，不宜降為 Medium。
- **建議修法：** **維持 High。** 每類沿用結果必須保留自己的基準依據；明定何種主檔才允許套用破壞性的隱藏。不能只用「主檔不比 base 舊」視為相容。無法確認時採既有版本不一致紅色警示，並禁止未驗證的隱藏；不必修改主檔 schema 或引入後端。

### R4｜High｜跨類別部分成功仍可讓公告兩邊都消失

- **問題：** 主檔 X 在 s3；網站把 X 移到 s4。此次 s3 成功，產生 supersedes X；s4 失敗且沒有舊 addition。前端隱藏 s3 的 X，但沒有 s4 的 X，缺藥公告完全消失。這與 zombie 規則無關，因此上一輪 **2.4「跨類交互只剩 zombie」的判定錯誤**。
- **晚修成本：** 會改變「各類獨立成功即可套用全部差異」的核心契約，並影響沿用及發布測試。
- **建議修法：** 分開定義新增與隱藏的安全條件。可繼續顯示成功類別的新公告，但來源類別缺席不足以證明目的類別已成功承接；無法確認時保留原有公告並使用既有 error 警示。這與 N8 相容，也不要求整批全有全無。

### R5｜Medium｜實測頁數與 D7 的固定頁容量互相矛盾

- **問題：** 若非末頁固定 15 筆：
  - 19 頁至少有 `18×15＝270` 筆非末頁資料，不能總共只有 244 筆。
  - 32 頁至少有 `31×15＝465` 筆非末頁資料，不能總共只有 406 筆。
  
  因此「19／32 是實際資料頁數」「244／406 是逐列總數」「非末頁固定 15 筆」至少一項不成立。
- **晚修成本：** 正常網站會被完整性守門直接拒絕，所有連網驗收失敗後才需重訂翻頁前提。
- **建議修法：** 先核對頁數是資料頁、請求次數還是其他計數，以及筆數是否經去重；以每頁原始資料列數定案 D7。不能直接把目前兩組數字都當成立的設計證據。

### R6｜High｜D7 是異常篩檢，尚不足以證明可安全隱藏

- **問題：**
  - 翻頁期間前面頁面的案件被刪除或移走，後續列向前位移，可漏掉一筆而沒有重複案件、沒有日期逆序。
  - 讀過第一頁後，新公告加入已讀區域，後續掃描不必然能看見它。
  - s3、s4 分別掃描期間案件移類，可能兩邊都沒讀到。
  - 分頁控制失效造成提早結束，或末頁少解析一筆，仍可能通過數量門檻。
  - 列表取得後、詳情取得前發生修訂；目前只要求案件與類別相符，沒有要求詳情品名／日期仍對應列表版本。
- **晚修成本：** 「單類完整快照」若其實是多個時間點拼接，差集刪除模型的安全前提就不成立，需回頭補觀測有效性契約。
- **建議修法：** 定義本次結果代表的觀測範圍，以及掃描中可見變動、列表／詳情不一致時的失敗條件。無法確認完整性的快照不得產生可信的隱藏結果；使用原有 error 即可。有限次掃描不能保證捕捉完成後才發布的公告，不應把這種合理時間界線與掃描中漏列混為一談。

### R7｜Medium｜`max(3, 2%)` 無法同時保證安全與正常修訂不中斷

- **問題：**
  - O＝238 時，依直接數值比較最多容許 4 筆 supersedes；O＝406 時最多 8 筆。少量改版誤解析仍可造成 1–4／8 筆靜默隱藏。
  - O＝16、L＝15，漏一筆仍通過 90% 與 supersedes 上限。
  - 正常修訂超過上限也會 error；若 opendata 長期凍結，差異可能持續超標，補抓就長期停止更新。
  - 正確的「尚無資料」若 O 非零，仍可能違反 90% 守門；A5 的無條件 ok 與 D7 未定優先序。
- **晚修成本：** 上線後容易為恢復運作而臨時放寬門檻，實際改變隱藏安全標準。
- **建議修法：** 將門檻定位為保守熔斷，不能稱為完整性證明。明定整數邊界、空集優先序，以及確認為真實大量變動後如何恢復成功查核；不得自動放寬以消除 error。接受正常大量修訂暫時誤報 error，與目前風險權重相容。

### R8｜Medium｜品名差異不是一律有害，但目前仍有未定義的錯配情境

- **問題：**
  - **同案件品名更正、K 改變：** 在完整、穩定、無碰撞且未超門檻的快照下，舊列隱藏、新列新增，模型可以正常處理。
  - **兩來源固定用字不同：** 也會形成一組新增／隱藏，未必漏報，但可能永久無法歸零，或大量觸發門檻。
  - **NFKC、去全部空白、只取首行造成 K 碰撞：** 不同公告可能被當作相同；中文內部換行也可能讓「第一行」丟失部分品名。
- **晚修成本：** 正規化一旦成為持久差集鍵，後續修訂會改變所有新增／隱藏結果。
- **建議修法：** 區分「可接受的文字格式等價」與「不能證明等價的用字差異」；明定中文欄位內換行與中英文分隔的界線。碰撞依 R2 處理；G3 改成上游在既定比較語意下真正一致才歸零，不保證不同命名慣例自然消失。

## 1. 仍未閉合與新增問題

### S1｜Medium｜s2「只用列表」無法產出符合契約的新增公告

- **問題：** §6 規定 s2 只用列表，但列表欄位沒有許可證字號與完整供應狀態；additions schema、§6.2 及既有清洗卻需要這些欄位。A10③ 的「s2 additions 含 X」目前沒有完整資料來源。
- **晚修成本：** 實作到 s2 真正出現新增案件才會發現無法通過驗證；以空值填補又會影響 zombie 判定及畫面內容。
- **建議修法：** 區分「不比較既有 s2 成員的內容」與「取得新增 s2 成員的完整資料」。新增公告仍須具備契約所需欄位及來源驗證；這不違反 N9，也不等於對 s2 全量做內容修訂偵測。

### S2｜High｜D10 停止 supersedes，不等於停止隱藏缺藥

- **問題：** D4 允許沿用失敗類別的 additions。假設 s2 的舊 additions 有 X 的恢復公告，這次 s2 error；D10 雖停用 supersedes，舊恢復公告仍加入 106，隨後 `cleanSupplyData` 仍可能刪除 104／105 的 X。因此：
  - B2「同樣情境但 s2 error → X 仍在 104」不一定成立。
  - B8「沒有任何主檔列被隱藏、additions 照常顯示」與 N2 不相容。
  - 這不是重新要求修改 zombie 規則，而是新增的失敗保護承諾未成立。
- **晚修成本：** 須重訂哪些 additions 在失敗／過期／版本不相容時仍可使用，影響資料套用及整組驗收。
- **建議修法：** 將 D10 的保護條件涵蓋「會透過既有清洗造成缺藥消失的補抓輸入」，不能只限制 supersedes。與 N2 相容的作法，是限制不可信恢復資料的納入資格，保留可信缺藥新增；不修改清洗函式。B8 應以「僅主檔經既有清洗的可見集合」作保留基準，而非承諾保留所有原始主檔列。

### S3｜High｜指紋只能防止刪掉不同內容，不能證明舊刪除指令仍有效

- **問題：** r3 已修好「較新主檔內容不同卻被舊 supersedes 刪掉」的一部分，但仍有兩個界線：
  1. 新主檔重新出現同身分、同指紋的公告，可能是網站重新納入原版本；舊補抓仍會隱藏它。B8 現在直接規定「指紋相同 → 隱藏」，等於接受此風險，不能再描述成已證明跨版本安全。
  2. s2 根本沒有內容指紋，第二輪判定所稱「整列指紋全部相符」並不適用於它；supersedes 又帶證號，D6 的 s2 身分卻不含證號，實際隱藏匹配條件仍不明確。
- **晚修成本：** 跨版本有效性若仍有歧義，後續須修改相容性契約及 s2 隱藏身分，不能只補一個測例。
- **建議修法：** 分開定義「精確匹配某列」與「該次缺席觀測仍可用於目前主檔」。對不同基準的主檔，須有明確的隱藏適用條件；無法確認時維持紅色警示及保守保留。若選擇接受同內容重新出現仍被隱藏的限制，必須明寫，不能宣稱 R3 已全面消除。另須明定 s2 的匹配欄位及重數處理，不藉此擴張成 s2 內容修訂偵測。

### S4｜Medium｜歷次表「同日期取第一列」的有效性尚未證明

- **問題：** 摩法爾第一列與 opendata 相符，只證明它與目前主檔相符，不能證明第一列就是該日最新、有效的網站說明。若第二列才是同日修訂，固定選第一列正好會漏掉 P3 要捕捉的修訂。
- **晚修成本：** 所有指紋與內容驗收都可能以錯誤版本作為標準；之後須重做內容比對結果。
- **建議修法：** 明定同日期多列的權威順序依據。若無法確認且內容不同，使用現有類別 error，不任選一列宣告內容一致；同日期內容完全相同的重複列可另行定義為無歧義。不能單以「與舊 opendata 相等」作為選取正確性的證據。

### S5｜Medium｜兩輪列表掃描沒有包住詳情階段，且「有歷史日期」不等於版本一致

- **問題：** 資料流是兩輪列表完成後才取得詳情。若列表日期是 10/07，網站在詳情抓取前更新為 10/26，而歷次表仍保留 10/07：
  - 依 §6 的選法仍能找到 10/07；
  - 若 D7 的「詳情日期相同」只驗所選歷史列，就會通過；
  - 實際取得的是已非列表目前版本的歷史說明。
  
  同日文字變動則不會改變兩輪列表；D8 無法證明內容在整個執行期間未變。
- **晚修成本：** 「查核成功時間」及「掃描中網站變動必報錯」會被賦予超過實際能力的保證。
- **建議修法：** 區分詳情的目前公告版本與歷史列存在性，明定兩者與列表的對應條件。將觀測承諾限定為實際驗證的時間範圍與可觀察差異；不要求靜態爬取做到原子快照，也不需要無限增加掃描輪數。

### S6｜Medium｜兩輪相同仍不能辨識穩定的提早截斷

- **問題：** D7 允許末頁 1–13 筆，非末頁恰為 13 筆。因此 A2(g)「分頁控制消失、但不是末頁筆數」無法涵蓋滿 13 筆的提早截斷。
  
  例如 O 有 27 筆，兩輪都只讀到前兩頁共 26 筆；案件不重複、日期正確、supersedes 只有 1 筆，D9 也通過。兩輪一致只證明重現同一結果。
- **晚修成本：** 可能把改版造成的固定漏頁當成成功快照，並產生合法的隱藏結果。
- **建議修法：** 明定有效末頁的頁面／分頁狀態證據，不能用列數判定滿頁是否為末頁。若網站沒有可獨立確認的證據，應承認對「穩定且外觀合法的截斷」仍有殘餘限制，不能把兩輪掃描稱為完整性證明。

### S7｜Medium｜等重數不代表 s3／s4 沒有內容差異

- **問題：** A6 寫「同身分兩邊都 2 次 → 無差異」，但 s3／s4 還有指紋：
  - O 指紋為 A、B；
  - L 指紋為 A、C；
  - 身分次數都是 2，仍應有 B 被替換成 C。
  
  奔麗生是 s2，不能拿它證明 s3 的等重數群組沒有差異。前端「主檔已有相同列就略過」也仍是存在性判斷，未明文遵守多重集合數量。
- **晚修成本：** 兩端可能各自通過測試，卻對碰撞群組採不同差集語意。
- **建議修法：** 將 s2 等重數對照與 s3／s4 指紋多重集合分開。明定差集、隱藏、略過新增均以完整比較單位及數量為準；最終再接受 N2 的完全重複去除。不要把既有清洗後恰好相同，當作前段差集正確的證據。

### S8｜Medium｜不支援的品名結構只記 log，未閉合 G2

- **問題：** 主檔品名有 0 或 2 個換行時，永不隱藏是保守選擇，但規格仍可能將該類標為 ok、沒有差異、前端不顯示警示。這時「完整比較成功」其實未成立。§6.2 又允許沒有英文時不附換行，需區分正常資料與不可比較結構。
- **晚修成本：** 會產生只能從本機 log 看見、前端卻宣告無差異的失敗路徑。
- **建議修法：** 明定這些列是否仍可可靠比較；若不能，使用既有類別 error／紅色警示並保留列，不新增 UI 狀態。若可比較，則不要僅以換行數決定其永久不可隱藏。

## 2. D10 的持續誤報與 UI 風險

### S9｜Medium｜長期不隱藏可以接受，但新舊說明並列不能默認安全

- **問題：** 某類長期 error、超出 40 頁或持續熔斷，會讓所有類別長期停止 supersedes。這是 D10 的必然結果；期間修訂公告可能同時保留舊版與新版，甚至同日期但替代藥說明不同。現有「公告頁補抓」徽章只說明來源，不能清楚表達目前存在未完成的版本替換。
- **晚修成本：** 功能驗收可能將「多顯示」一律視為保守正確，直到藥師採用舊替代藥說明才發現問題。
- **建議修法：**
  - **接受持續性多顯示的取捨**，不以逾時或長期 error 自動恢復隱藏；這符合寧可誤報的風險權重。
  - 明定現有紅色警示須說明「目前保留舊版本，可能與補抓版本並列，供應說明須核對官網」，不能只寫某類抓取失敗。
  - 對可確認的修訂對照，既有來源與警示資訊必須足以辨識兩個版本，不把它們無提示地當成兩筆獨立且同時有效的建議。
  
  這是既有 G2 警示與 G1 合併顯示的語意補全，無須新增「待核對」狀態或視覺改版。

## 3. 新增／改寫驗收的弱化通過路徑

| 條件／嚴重度 | 可通過但仍壞的弱化版本 | 為什麼晚修更貴 | 建議改寫斷言 |
|---|---|---|---|
| **A1／Medium** | 只驗 additions；相同身分的既有公告不抓詳情，仍通過所有 addition 對應案例。或固定取同日第一列，恰好通過摩法爾。 | P3 核心功能沒有被驗證。 | 加入 O 已有成員、日期不變但內容修改的完整流程；對同日不同內容及「歷史日期存在、目前版本已更新」驗證 S4／S5 的定案結果。 |
| **A2／Medium** | 允許讀第 41 頁，只要第 41 頁沒有下一頁就成功；或把完整 13 筆的截斷頁認為末頁。 | 頁數與終止規則在真實站才暴露。 | 加入「第 40 頁仍有下一頁」及「第 41 頁恰為末頁」均不得成功；另測 13 筆頁面的分頁狀態破損，不使用「不是末頁筆數」作判據。 |
| **A6／Medium** | 同身分等重數就直接判無差異，忽略指紋分布；或直接將所有無換行列排除比較。 | 固化 S7／S8 的錯誤語意。 | 分列 s2 與 s3／s4 的重數案例；斷言 A、B 對 A、C 的完整差集。不可比較列必須驗證對外狀態，不能只驗「未出現在 supersedes」。 |
| **A10／High** | s2 addition 只有案件編號；移類序列仍以「含 X」通過。失敗回退只驗陣列存在，沒有驗恢復公告的後段效果。 | 跨次與跨類資料鏈不完整。 | ③斷言完整合法 s2 record；新增「s2 失敗但沿用非空恢復 additions」序列，經完整清洗後驗證 S2 定案的缺藥保留結果。 |
| **A11／Medium** | 模擬 push 永遠成功，或只驗 base 不變；最後 push 失敗仍回 exit 2，被當成已發布 error 快照。 | 抓取錯誤與發布失敗無法區分。 | 明列抓取部分失敗但發布成功、重試發布成功、重試仍失敗三種結果；驗證最終發布內容與狀態，不能只驗指令出現。無須真實雙機競爭。 |
| **A12／Medium** | 永遠重試，重試後永遠 error；目前沒有「第二次兩輪一致後成功」案例。兩輪結果不同也可能不關心資料順序以外欄位。 | 重試無法恢復，或實際漏比欄位。 | 加入第一次不一致、重試穩定後成功，且成功結果只能來自重試觀測；逐一改案件、品名、日期及順序，驗證比對契約。不能據此宣稱詳情內容也經兩輪確認。 |
| **B1／Medium** | 同樣錯誤輸入穩定產生同樣錯誤結果，符合純函式與不變性；多重集合選錯仍通過。 | 純函式性質被誤當業務正確性。 | 為重數案例寫明各筆指紋及精確保留對象；分別斷言清洗前套用結果及 N2 後結果。`O 兩筆、supersedes 一筆`須有與 D7 相容的完整情境。 |
| **B2／High** | 在 s2 error 反例中把 additions 清空，便能證明 X 留在 104；但 D4 允許的非空沿用結果會刪掉 X。 | 測試避開真正危險路徑。 | 反例必須沿用有效、非空的 s2 恢復 additions，並驗證最終 UI 集合；按 S2 修訂安全契約。 |
| **B3／Medium** | 只處理日期改變的修訂，同日不同內容仍並列，照樣通過。 | 最重要的新功能未受前端驗收保護。 | 加同身分、同日期、不同指紋的替換正例，以及 D10 不成立時的雙版本與紅色警示案例。 |
| **B8／High** | 僅檢查 supersedes 沒有執行，忽略 additions 經清洗後刪列；正例又刻意允許舊指令隱藏較新主檔的相同內容。 | 驗收保護了錯誤安全承諾。 | 以僅主檔清洗結果作比較，加入非空 s2 additions；對跨版本相同內容重新出現，依 S3 明確定案，不能以指紋相等直接等同安全。 |
| **B9／Medium** | reload fixture 保留相同 `編號`，便證明 key 穩定；實際主檔若重編號，展開狀態仍可能錯置。 | 身分前提直到真實更新才被推翻。 | 先證實 opendata `編號` 的跨更新穩定性；若無此保證，驗收應要求資料變動時不得把展開狀態移給另一案件，而不是無條件保證跨 reload 保持展開。 |
| **C1／Medium** | 獨立腳本只核對 s3，s4 內容比較與 s2 新增資料仍可能壞；兩支腳本都選同日第一列也會一致。 | 第二套流程一致不代表來源版本正確。 | 連網可得範圍核對三類；目前無真實差異的路徑由已定案 fixture 補足。同日多列的版本選擇另有來源依據，不能只看兩支腳本一致。 |
| **C3／Medium** | 人工也照規格選第一列，逐字比對全過，但官方有效版本可能是另一列。 | 人工驗收複製同一個錯誤前提。 | 人工確認先判定有效的歷次版本，再比文字；supersedes 的「已不存在該版本」須指目前有效版本，不是歷史表完全找不到。 |
| **C4／High** | 單類 error 只有非空 supersedes，沒有恢復 additions；測試仍避開 S2。雙版本只驗筆數，不驗使用者看到的矛盾說明。 | 正式失敗情境才出現漏報或錯用舊說明。 | 加入 s2 error／過期且沿用恢復 additions、同日內容修訂雙版本，以及同證案件的最終可見結果與警示文案。 |

**A5、C2 本輪未發現新的獨立缺口**；不為湊反例而擴張它們的責任。

## 4. 可削減的過度設計

| 嚴重度 | 問題 | 為什麼晚修更貴 | 建議修法 |
|---|---|---|---|
| **Low** | C1 強制另寫一支獨立腳本，可能形成第二套完整擷取器，且仍會共享同一錯誤規格前提。 | 增加維護量，卻未必增加來源版本判定的可信度。 | 將要求改為獨立、可追溯的核對結果；不強制特定工具形式。若使用一次性核對腳本，不必讓它承擔長期正式管線責任。 |
| **Low** | 「純函式天然冪等」用詞不準確。相同原始輸入結果相同是確定性；冪等是重複套用結果不變，兩者不同。 | 容易重新引入前兩輪已排除的驗收誤解。 | D2 保留「每次由原始主檔計算、相同輸入結果相同」，刪除天然冪等的宣稱。 |
| **Low** | 兩輪列表與全類隱藏門檻有明確目的，不能單為縮短流程移除；但也不應為追求不存在的原子快照無限增加輪數。 | 增加時間、失敗率，仍無法證明整段期間完全無變動。 | 保留有限觀測與保守失敗策略，精確描述其保證及限制。優先解決 s2 完整資料與間接刪除，毋須再擴充狀態種類。 |
