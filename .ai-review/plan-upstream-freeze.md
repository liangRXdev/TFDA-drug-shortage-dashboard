# 規格：上游停更偵測（upstream freeze detection）

> 增量代號 **F**（Freeze）。撰於 2026-09-08，**修訂 r2**（依 `plan-verdict-upstream-freeze.md`）。
> 基線：`main` @ `db5265f`，測試全綠 = pytest 20 + vitest 71。

---

## 1. 問題

`fetch_fda_data.py` 的 `build_payload()` 把 `last_updated` 設為 **`datetime.now(TAIPEI_TZ)`**，
每次成功執行都蓋成當下時間，**與上游內容是否改變無關**。
前端 `isDataStale()`（`src/lib/dataPipeline.ts:91`，`STALE_THRESHOLD_DAYS = 10`）即以此欄位判定時效。

**後果**：只要 Actions 還在跑，「資料過期」警示永遠不會亮。TFDA 若停止發布新公告，
儀表板每週五照常 commit、導覽列照常顯示「資料更新：（今天）」，畫面上無任何跡象，
臨床看到的「目前 254 項缺藥」實際可能停在數月前。

### 1.1 這不是 CR-06 判錯，是兩種凍結模式

| 凍結模式 | 現象 | 現行防線 |
|---|---|---|
| **A. 排程停跑**（CR-06 原情境：GitHub 對 60 天無活動 repo 自動停用 scheduled workflow） | `last_updated` 不再前進 | ✅ `isDataStale` 有效 |
| **B. 排程照跑、上游凍結**（本規格） | `last_updated` 每週前進，內容不變 | ❌ 三道全部看不到 |

CR-06 的設計對模式 A 正確且必要，**不得移除**。本增量補的是模式 B。

### 1.2 為何現有三道防線都擋不到模式 B

- `check_sanity` 的 `DRASTIC_DROP_RATIO`：凍結時筆數**不變**，不是驟降
- fail-closed / sentinel 辨識：上游正常回應 200 與合法結構，不是抓取失敗
- `isDataStale`：量的是 ETL 執行時間，恆為今天

## 2. 現況證據（2026-09-08 實測，上游是活的）

| 資料集 | 筆數 | `max(公告更新時間)` |
|---|---|---|
| `54504_with_alternative` | 254 | 2026/08/31 |
| `54505_no_alternative` | 0（sentinel，合法空集） | — |
| `54506_resolved` | 400 | 2026/08/27 |

`last_updated = 2026-09-04 04:10:50`；近半年月公告量 3–13 筆（**每月均有公告**）。
**本增量為預防性修補，非救火。**

## 3. 目標 / 非目標

**目標**

1. 讓「上游最大公告日期是否前進」成為 payload 中的一級事實，而非由 ETL 執行時間代理
2. 前端能在模式 B 下顯示與模式 A 有所區別的**疑似**訊號
3. 保留模式 A 的既有防線不退化

**非目標（範圍蔓延錨點）**

- 不改抓取來源、不新增端點、不改 fail-closed 行為
- 不改替代藥 regex（CR-07）、不做去重（CR-08）、不動排序（CR-09）
- 不引入通知管道（email／LINE／issue 自動開單）——本增量只到「畫面上看得見」
- 不改 `STALE_THRESHOLD_DAYS` 既有語意，不移除 `isDataStale`
- **不做逐端點停更偵測**（B2-4）。本增量只看**全域**最大日期，一個端點前進即會清零另外兩個端點的訊號。**未告警不代表三端點皆正常。**
- **不做全文雜湊、逐端點歷史、內容比對**（B4-2）。內容不變仍無法證實停更，且會擴大資料模型。明文接受**同日修訂與局部停更會漏報**。
- 不引入三態列舉型別或狀態機框架（B4-1）；`null` 已足以表達「不可判定」

## 4. 設計

### 4.1 為何用「未前進次數」而非「距今 N 天」

**先更正一項先前的錯誤主張（B2-1）**：本偵測器**並非**與公告疏密無關。
固定週排程下「連續 N 次未前進」≡「約 N 週無新公告」，只是把「天」換成「次」。

真正的理由是**可觀測性**，不是不受疏密影響：

- 「距今 N 天」需在前端以 `Date.now()` 比對，會隨使用者開頁時間漂移，且與 `last_updated` 語意混淆
- 「未前進次數」在 ETL 端結算並寫入 payload，是**已發生觀測的事實**，前端只呈現、不再判斷

門檻的正當性來自實測（§2）：近半年每月均有 3–13 筆公告，
故「連續 4 個觀測區間無新公告」確屬異常。此為**經驗門檻，非理論保證**。

**因此結論只能是疑似訊號**：最大日期未前進**不等於**上游未更新
（同日修訂、舊公告修正、品項移動都不改變全域最大日期）。文案必須反映這點。

### 4.2 計數單位：觀測區間（B1-1）

**`frozen_runs` 以「觀測區間」為單位，不是以「執行次數」為單位。**
觀測區間 = 該次執行所屬的 ISO 週（`YYYY-Www`，台灣時間）。

- payload 新增 `last_observed_period`（如 `2026-W36`）
- 同一區間內重跑（手動 dispatch、retry）：**照常更新資料與日期，但不重複累加** `frozen_runs`
- 不同區間且日期未前進：`frozen_runs += 1`，`last_observed_period` 更新

若無此規則，一天內手動跑 4 次即可觸發告警——與低誤報取捨直接衝突。

### 4.3 日期有效性與不可判定狀態（B1-2、B1-3、B1-4、B4-1）

**有效日期**須同時滿足：為字串、`strip()` 後符合 `YYYY/MM/DD`、且為**真實曆日**
（`2026/02/30`、`2026/13/01` 無效）。未來日期視為有效但記 warning（不阻斷）。
缺值、非字串、空白一律視為無效。

`upstream_max_date` 為**有效日期字串或 `null`**（舊 payload 可缺欄）。

**`null` 表示「無可比較基準」，絕不可當作「與前值相等」。**
狀態轉移：

| 前值 → 本次 | `frozen_runs` | 說明 |
|---|---|---|
| 有效 → 更大 | 歸零 | 上游前進 |
| 有效 → 相等 | +1（同區間則不變） | 未前進 |
| 有效 → 更小 | 歸零 + warning | 上游撤回公告，重建基準 |
| 有效 → `null` | **凍結不動**（不加不減） | 不可判定，中斷累計 |
| `null` → 有效 | 歸零 | 重新建立基準 |
| `null` → `null` | **凍結不動** | 不可判定 |
| 缺欄 → 任意 | 歸零 | 保守起步 |

**不可判定時前端不顯示停更提示**（漏報側，符合風險權重）。

**格式漂移的退化方向已更正（B1-3）**：先前 §6 稱「只會誤報凍結，方向安全」是**錯的**——
本專案風險權重是寧可漏報也不要誤報，誤報凍結正是不可接受的一側。
且僅「最新列」漂移、舊列仍可解析時，最大日期會**假性停住**，不需全部無法解析即觸發。

**因此改為**：本次觀測若存在無效日期，視為可信度受損 → **本次不累積凍結證據**
（`frozen_runs` 凍結不動）。無效日期只影響「是否採計為最大日期候選」，
**不刪除公告列、不繞過既有結構驗證**；CR-01／CR-02 的失敗仍一律 fail-closed。

### 4.4 前版狀態契約（B1-5、B1-6、B2-3）

**唯一基準是 repo 已接受的 payload**（`actions/checkout` 取得者），不是 runner 本機檔案。

| 前版情況 | 處置 |
|---|---|
| 首次無前檔 | `frozen_runs = 0`，建立基準 |
| 合法舊 schema（無偵測欄） | `frozen_runs = 0`，保留既有資料 |
| 只缺其中一欄 | 視為狀態無效 → 歸零重建 |
| `frozen_runs` 為負數／小數／字串／`NaN`／`Infinity` | 視為狀態無效 → 歸零重建 |
| 日期與計數互相矛盾（有計數但無日期） | 視為狀態無效 → 歸零重建 |
| 前檔存在但無法讀取／解析 | **fail-closed**：非零結束、不覆寫正式檔，**不得**默認為首次執行 |

`frozen_runs` 須為非負整數。

**`git push` 失敗的行為已核對**：該步驟非零退出、job 紅燈，且下次 `checkout` 仍取得舊 payload
並從該基準重算 → 結果是**少累加一次**（漏報側，可接受），不是狀態遺失。

**並行控制（B2-2）**：為 `update_data.yml` 加 `concurrency` group（比照 `deploy.yml:20`），
確保同時間只有一個 ETL 執行。**不在規格層自建跨執行狀態承接協議**——
那等於在無伺服器狀態的靜態管線上做分散式共識，與平台限制衝突。

### 4.5 payload schema（向後相容雙向）

```jsonc
{
  "last_updated": "2026-09-04 04:10:50",  // 語意不變：ETL 最後成功「檢查」時間
  "upstream_max_date": "2026/08/31",       // 新增：有效日期字串，或 null
  "frozen_runs": 0,                         // 新增：連續幾個觀測區間未前進，非負整數
  "last_observed_period": "2026-W36",      // 新增：計數單位（ISO 週，台灣時間）
  "datasets": { }
}
```

- 舊前端讀新 payload：多出欄位被忽略，行為不變
- 新前端讀舊 payload（缺欄）：`isSupplyData` **不得**因缺欄判為無效；偵測欄視為 `undefined`，停更提示不顯示，退回現行行為

### 4.6 前端變更（`src/lib/dataPipeline.ts`、`src/App.tsx`）

1. `SupplyData` 加 `upstream_max_date?: string | null; frozen_runs?: number; last_observed_period?: string`
2. 新增 `FROZEN_RUNS_THRESHOLD = 4` 與 `isUpstreamFrozen(data)`。
   回 `true` 僅當：`frozen_runs` 為 **≥ 門檻的非負整數** **且** `upstream_max_date` 為有效字串。
   缺欄、字串、布林、`null`、負數、小數、`NaN`、`Infinity`、無可比較日期 → 一律 `false`。
3. 導覽列文案：
   - 現行「資料更新：{last_updated}」→ **「最後檢查：{last_updated}」**
   - 新增「上游最新公告：{upstream_max_date}」（有有效值才顯示）
   - `isUpstreamFrozen` 為真時顯示：**「已連續 N 次觀測未見上游公告日期前進，清單時效需留意」**（刻意不寫「上游已停更」——這是疑似訊號，見 §4.1）
4. 模式 A（`isDataStale`）提示保留不動；**兩者可同時成立，各自顯示，互不遮蔽**

## 5. 驗收條件

> 每條均已針對「能通過驗收但功能是壞的」弱化實作加以堵死（依 plan-verdict 區塊 3）。

| ID | 條件（斷言的是性質，不是存在） | 驗證方式 |
|---|---|---|
| F1 | 三端點**各自**成為唯一最大值來源時皆正確；各含多列、空集、同日、跨月／跨年。**任意調換列序與資料集序，結果不變**；無效日期不得成為最大值 | pytest |
| F2 | 混合有效與無效日期時：有效日期仍被萃取為最大值、**公告列全數保留**、可信度標記為受損、**且不累積凍結證據**。反例須含假曆日（`2026/02/30`）、非字串、空白、`2026-08-31`、`N/A`，以及**最大日期所在列無法解析**的情形 | pytest |
| F3 | 端到端：**三端點皆 sentinel 時維持 fail-closed 不發布**（既有 CR-01 不變量，見下方修正）。`upstream_max_date = null` 的可達路徑改以「資料非空但日期全無效」驗證：正常發布、`null`、`frozen_runs = 0`、前端無提示。另測有效→`null`、`null`→`null`、`null`→有效三種轉移。任一端點回原始 `[]` 且無 sentinel 時非零結束、正式檔不變 | pytest + vitest |
| F4 | 日期前進 → 歸零**且基準確實更新**：以該次發布結果承接下一次相等觀測，應得 1（僅驗「回零」可被「永遠回零」矇混） | pytest |
| F5 | 從基準 0 起，**三個不同觀測區間**逐次承接 repo 已接受 payload → 1、2、3。**同區間重入不累計**；失敗或未被 repo 接受的結果不累計 | pytest |
| F6 | 從非零狀態遇日期倒退 → 發布回退日期與零計數，warning **內容須含前後日期**；下一次與回退日期相等的觀測應得 1（僅驗「有 log 輸出」可被任意 logger 矇混） | pytest |
| F7 | 分別驗：首次無前檔／合法舊 schema／只缺任一欄／`null`／負數／小數／字串計數／日期與計數矛盾／前檔不可解析，各自結果須符合 §4.4 契約（最後一項須 fail-closed，**不得**當成首次執行） | pytest |
| F8 | 固定**兩次不同檢查時刻**、同一上游日期、非零前版：斷言 `last_updated` 隨檢查改變、`upstream_max_date` 不變、`frozen_runs` 依規則轉移、**`datasets` 內容不受偵測欄位影響**。另驗 `null` schema | pytest |
| F9 | 每個端點分別發生連線／非 200／JSON／結構錯誤，**以及狀態計算失敗、原子替換失敗**時，均非零結束且正式檔**逐位元不變**（含舊時間與舊計數）。原始空陣列異常亦走此路徑 | pytest |
| F10 | 合法舊 payload 與合法新 payload 皆回 `true`；**核心欄位結構錯誤仍須回 `false`**（僅驗舊 payload 通過可被「永遠回 true」矇混）。偵測欄無效時停用偵測但不否決清單 | vitest |
| F11 | 完整有效狀態下 3 → `false`、4／5 → `true`；缺欄、字串、布林、`null`、負數、小數、`NaN`、`Infinity`、**有計數但無有效日期**均 → `false`。日期距今多久**不得**單獨決定結果 | vitest |
| F12 | `isDataStale` 解析與 10 天門檻邊界行為不變，新欄有無皆不影響；**並驗 UI 的 A／B 四種組合**——兩者同時成立時**兩個提示都要看得見** | vitest |
| F13 | 舊 payload：正常呈現清單與「最後檢查」，無日期列、無停更提示、不報錯。新 payload 未達門檻：無提示。**達門檻：必須顯示提示、N 值正確、文案與模式 A 不同**。不可判定狀態不誤報（僅驗「舊 payload 不顯示」可被「永不顯示」矇混） | vitest |
| F14 | 完成條件為 **F1–F13 的性質逐條對照**，指定案例不得跳過；既有保障不得以刪除或弱化斷言換取綠燈。**測試數僅供參考，不作為完成條件** | 兩套測試 |
| F15a | **狀態機以固定觀測序列驗證**（可控、可重現）：涵蓋短時間重跑、合法空集、格式漂移、不可判定恢復、同日內容變更、正常稀疏公告六類反例 | pytest |
| F15b | **發布鏈以實跑驗證**：手動 `workflow_dispatch` 後核對 Actions 綠燈、repo 正式 payload 內容、**公開頁面實際畫面**三者一致。允許差異須列名（`last_updated` 必變；上游若真的變動則日期與計數亦可變）。**不得要求「第二次必 +1 且無其他 diff」** | 實跑 Actions |

**F15 原條文已作廢**：「驗冪等」與「第二次 `frozen_runs` 應 +1」直接衝突，
「無其他 diff」又與「每次成功更新 `last_updated`」衝突——三者無法同時成立，
該條**數學上不可滿足**。拆為 F15a／F15b。

## 6. 風險與取捨

- **這是疑似訊號，不是停更證明。** 同日修訂、舊公告修正、局部端點停更均不會觸發（明文接受漏報）。
- **門檻為經驗值**：依 §2 實測（每月均有公告）訂為 4 個觀測區間。不建議低於 3。
- **`frozen_runs` 依賴 repo 已接受的前一版**：commit 被人工還原時會沿用被還原版本的狀態；缺少或無效才重建基準。**不保證曆時上限**——後續失敗、不可判定或再次還原都會延長延遲。接受此取捨：寧可漏報也不要對缺藥資訊誤報。
- **無效日期使本次不累積證據**：上游格式漂移時偵測器暫停而非誤報，方向與風險權重一致。
- **字串比較的成立條件**：僅在通過 §4.3 有效性檢查後才比較，此時格式固定為 `YYYY/MM/DD`，字串序等同日期序。
